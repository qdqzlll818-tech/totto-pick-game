# 移动端性能、黑蒜与 2.5D 物理修复报告

## 测试环境

- 基线提交：`ba3f97c20e527e920f43aaea63cd8d61d8d49dd4`
- 视口：`390 × 844`（iPhone Safari 常见纵向尺寸）
- 浏览器：Chromium 内核移动视口
- 性能时间：从导航开始到当前关卡的唯一图片完成解码、物品分批挂载完毕并可操作
- 冷启动：使用同源下未缓存的 v11 脚本和 WebP URL；缓存启动：随后重载

本地浏览器数据不是 iPhone 真机跑分，也没有把本地服务器伪装成真实运营商网络。普通 4G 结果根据实际传输体积估算，并在“已知限制”中单独标注。

## 根因

### 开场加载

1. 原实现同步创建并逐个插入当前关卡的全部物品节点，大蒜局一次创建 108 个，冬日局最高 168 个。
2. 每次选取、撤回、道具或三消后都会清空物品容器，再完整创建全部剩余 DOM 和 `<img>`。
3. Supabase CDN 脚本是同步阻塞脚本；首次网络较慢时，游戏初始化必须等待它执行，但开局并不需要登录或云同步。
4. 原始后六关是 512px PNG；单关资源约 1.69–3.36 MB，而屏幕上的物品通常只有 84–116 CSS px。
5. 命中检测为每种素材读取完整分辨率 Alpha；512 × 512 素材会创建大画布并同步复制全部像素。
6. 每个物品容器有两层 `drop-shadow`，图片还有额外颜色滤镜；密集堆叠时首绘和合成成本随物品数增加。

### 黑蒜透明

- 配置路径原为 `assets/garlic/purple-garlic.png`。
- CSS 没有为黑蒜设置 `opacity` 或 `mix-blend-mode`，父元素也没有继承透明度。
- 原 PNG 中心像素 Alpha 为 `87/255`；深色主体的 Alpha 中位数约 `170/255`，所以白蒜、锅底和其他物品会透过主体。
- 修复素材 `purple-garlic-opaque.png` 的外部四角 Alpha 为 0，深色主体中超过 97% 的像素 Alpha 不低于 245，低于 200 的像素少于 2%，主要位于抗锯齿轮廓。

### 翻锅与移动过平

- 原 `applyBoardMotion` 对所有物品施加独立随机位移，再随机把少数物品提升一层。
- 状态只有 `x/y/layer/depth/rotation`，没有质量、半径、模拟高度、支撑、遮挡、速度和沉降状态。
- 抽取物品后没有计算依赖关系，也没有局部塌落；整锅重新渲染进一步削弱了连续运动感。

## 性能对比

|---|---:|---:|
| 大蒜局冷启动到可操作 | 3055.6 ms | 424.1 ms |
| 大蒜局缓存启动到可操作 | 143.5 ms | 136.9 ms |
| 图片请求数 | 14 | 14 |
| 当前关卡图片传输体积 | 628,466 B | 145,584 B |
| 当前关卡图片解码体积 | 624,266 B | 211,606 B |
| 物品 DOM 总量（稳定后） | 108 | 108 |
| 单帧初始挂载量 | 108 | 28（分 4 帧） |
| 开局长任务 | 1 × 50 ms | 0 |
| 最大长任务 | 50 ms | 0 ms |

稳态仍保留每个物品的独立节点，保证 Alpha 命中、遮挡、可访问性和 2.5D 动画；优化点是分帧挂载、持久复用节点，以及只更新受影响物品，不是减少玩法内容。

所有关卡当前实际引用的 115 个图片文件合计约 1.77 MB。原仓库全部 PNG/WebP 图片约 17.01 MB；原 PNG 保留为美术源文件，游戏配置改用 320px WebP，避免破坏原始素材。

以普通 4G 约 1.6 Mbps 粗略估算，大蒜局 145.6 KB 图片载荷约需 0.73 秒，再加 RTT、HTML/脚本和解码，预期仍在 3 秒目标内。这是传输体积推算，不代替真实运营商网络和真机测量。

## 2.5D 实现

- 每件物品增加 `x/y/z`、半径、质量、速度、角速度、支撑列表、遮挡列表、可见比例和沉降状态。
- 使用 15 单位空间网格寻找邻近物品；支撑和遮挡只比较周围网格，不在动画每帧执行全量两两碰撞。
- 抽取前沿支撑图做 BFS，只标记直接或间接依赖被抽物的物品；无依赖时不移动无关区域。
- 抽取动画先飞向收集槽；局部物品延迟 30–80 ms 后受重力下落，带横向偏移、旋转、接触回弹和 350–700 ms 沉降。
- 动画逐帧只更新 `transform`、旋转、阴影和层级；结束时一次性写回稳定 `x/y/z`，再重算命中与遮挡。
- 翻锅手势输出方向和强度，转为共享物理坐标中的冲量；上层、较轻、支撑较少的物品移动更多，底层物品移动更少。
- 所有目标坐标都投影回锅内椭圆；固定随机种子可复现同一沉降。
- `prefers-reduced-motion` 下跳过逐帧弹跳，只保留状态变化和简化阴影。

## 动作识别

- 低幅输入用于学习慢变化基线，并应用每轴死区，过滤静态偏置和轻微噪声。
- 必须在 80–420 ms 内出现方向余弦小于等于 -0.42 的反向大冲量。
- 中等阈值 10.5，强阈值 17；成功一次后冷却 1600–1800 ms。
- 第二段冲量映射到锅内方向，设备 z 轴会映射为纵向翻动，不再生成无方向随机位移。
- iOS 继续在用户点击后调用 `DeviceMotionEvent.requestPermission()`。
- 无传感器设备显示“轻翻按钮”，提供可见降级入口。

## 开发模式

正式页面不显示调试 UI。使用 `?dev=1&fresh=1` 启用：

- 碰撞范围、z/层级、支撑与遮挡、受影响物品、速度和沉降状态。
- “模拟抽取”和“模拟翻锅”按钮。
- `P` 键模拟确定性抽取，`F` 键模拟确定性强翻锅。
- `scene=collapse`：局部支撑塌落场景。
- `scene=opacity`：黑蒜覆盖白蒜的稀疏场景。
- `scene=match`：三件同类物品的收集槽/三消回归场景。
- `debug-ui=0`：保留确定性场景和模拟快捷键，但隐藏调试标记，便于录制验收素材。

## 已知限制

- 尚未在真实 iPhone 上读取传感器；阈值、z 轴映射和手感仍建议在 Safari 真机做一轮微调。
- 浏览器移动视口验证的是 Chromium，不是 WebKit 渲染器。
- 轻量物理使用圆形近似碰撞范围，不是完整刚体多边形物理；它优先保证 100–168 件物品时的可操作性和确定性。
- PR 在验收前不会合并到 `main`，因此稳定 GitHub Pages 不会被覆盖。
